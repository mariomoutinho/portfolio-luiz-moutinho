01 — Visão geral

Do pedido ao acompanhamento de status

O desafio era construir uma pequena aplicação de e-commerce sem isolar front-end e backend como exercícios desconectados. O fluxo precisava criar pedidos, consultar a lista persistida e atualizar o status com contratos consistentes de ponta a ponta.

Objetivo

Praticar uma cadeia completa entre interface e API, incluindo validação, persistência local e testes automatizados.

02 — Produto e domínio

Um escopo pequeno, mas completo

O MVP concentra o uso em duas ações principais: cadastrar um pedido e acompanhar sua evolução. A decisão de trabalhar com quatro estados — pendente, em processamento, enviado e cancelado — tornou explícita a linguagem do domínio em toda a aplicação.

  • Cadastro com nome do cliente e valor total.
  • Listagem abastecida pela API, sem pedidos fixos no front-end.
  • Atualização de status preservando o estado anterior quando a requisição falha.
  • Autenticação, paginação, busca e exclusão ficaram fora do escopo documentado.

03 — Solução desenvolvida

Interface, serviço e persistência alinhados

O front-end usa componentes standalone, formulários reativos e um serviço que centraliza as chamadas HTTP. No backend, uma Minimal API direciona as requisições para regras de serviço e um repositório com persistência JSON.

Fluxo técnico

  1. O formulário Angular valida os dados do pedido.
  2. O serviço envia a requisição ao endpoint correspondente.
  3. A camada de domínio valida e cria ou atualiza o pedido.
  4. O repositório grava os dados e a interface recebe a resposta.
  5. A tela atualiza o conteúdo e apresenta feedback.

Tecnologias

C#, .NET 8, ASP.NET Core Minimal API, Angular 22, TypeScript, Reactive Forms, Angular Material, SCSS, JSON, xUnit e Vitest.

04 — UX/UI e responsividade

Estados claros para uma operação cotidiana

A interface organiza formulário e listagem na mesma página. Em telas menores, os pedidos permanecem em cards sem rolagem horizontal. A aplicação diferencia carregamento, lista vazia e erro com nova tentativa, além de usar mensagens de feedback após criação ou atualização.

Rótulos de status ficam centralizados no modelo TypeScript, reduzindo divergências entre os dados da API e o texto exibido. Campos, botões, seletores e indicadores usam componentes Material, enquanto o layout responsivo permanece nos estilos locais.

05 — Testes existentes

Contratos verificados nos dois lados

A suíte do backend usa xUnit para regras do serviço, incluindo criação com status inicial e rejeição de status inválido. No front-end, os testes verificam requisições GET, POST e PATCH com HttpTestingController e confirmam que um formulário inválido não tenta criar um pedido.

A persistência em arquivo usa escrita temporária e bloqueio local para reduzir o risco de corrupção. Ainda não há testes de integração dos endpoints documentados.

06 — Aprendizados e próximos passos

Limites que orientam a evolução

O JSON atende ao objetivo de estudo em uma única instância, mas não substitui um banco relacional em um cenário de produção. Uma próxima etapa coerente seria adotar persistência relacional e testes de integração, mantendo as regras de domínio já separadas.

A demonstração publicada usa um adaptador PHP compatível com os mesmos contratos porque a hospedagem compartilhada não executa processos .NET. A implementação principal do repositório permanece em ASP.NET Core.
